## 🔧 実装に関するガイドライン

### コーディングスタイル
- 既存コードに合わせる。
- 関数やクラスの追加時は簡潔な docstring（日本語）をつける。
- 不要な最適化や過剰な構造変更は避ける。

### リファクタリング方針
- 大規模なリファクタリングは自動で提案しない。
- ただし、安全に改善できる場合は理由を付けて提案してよい。

### セキュリティ
- パスワード・秘密鍵・APIキーを含むファイルには触れない。
- `.env` を読むようなコードを提案する場合は必ず注意喚起する。

### LaTeX
- LaTeX を使用する際は、必ず `~/.latexmkrc` の設定を用いること。
- `latexmk` コマンドを提案する場合は、ユーザーの `~/.latexmkrc` が適用されることを前提とする。

### 数式の表記 (出力先で決める)

**数式の書き方は「何を書くか」ではなく「どこに出るか」で決める．** 判断基準はただ一つ，
**その数式を最終的に読む人が，LaTeX を描画する環境で見るかどうか**である．
下表の 2 つを混同しないこと．チャットのつもりでファイルに Unicode 数式を書いてしまう事故が
実際に起きている (2026-08-07，`docs/survey/` の全文訳 6 ファイル) ．

| 出力先 | 記法 | 理由 |
|--------|------|------|
| **チャット応答** (端末に直接表示される本文) | **Unicode** | CLI の TUI (Antigravity CLI / Claude Code) は LaTeX を描画しない |
| **ファイルに書く成果物** (`.md` / `.tex` / ノート等) | **LaTeX** | ブラウザ・エディタプレビュー・GitHub が描画する |

#### チャット応答 → Unicode

- 対象は端末に表示される本文だけ．ファイルへ書き込む内容は対象外．
- 避ける記法: `$...$`，`$$...$$`，`\frac`，`\sum`，`\int`，`\alpha` などの LaTeX コマンド．
- Unicode の書き方の例:
  - 上付き: x²，aⁿ，eˣ ／ 下付き: xᵢ，a₀，aₙ
  - ギリシャ文字: α，β，γ，θ，λ，μ，π，σ，φ，ω
  - 演算子・記号: ∑，∫，∏，√，∞，≈，≠，≤，≥，±，×，÷，·，→，⇒，∈，∂，∇
  - 分数は `a/b` と書く．込み入った式は等幅コードブロックで桁を揃えてよい．
- 行列・多段分数・極限付き積分など Unicode 化が難しい式は，等幅コードブロック内で整形する．

#### ファイルに書く `.md` → LaTeX

Markdown ファイルは端末ではなくブラウザやエディタプレビューで読む．**LaTeX で書くこと．**
Unicode と LaTeX 風添字を混ぜた `Σ_{i∈G} w_j (Y_{i,j}^t − Z_{i,j}^t)^2` のような
「なんちゃって表記」は，どの環境でも描画されないので**最悪の選択**．必ずどちらかに寄せる．

- インライン: `$X^{t+1}$`．表示: `$$...$$` を単独行に置き，**前後を空行で挟む** (GitHub の描画条件) ．
- 条件付き確率の縦棒は `\mid` を使う (`P(A \mid B)`) ．素の `|` は表内で列区切りと衝突する．
- 集合の波括弧は `\lbrace` `\rbrace`．`\{` は Markdown のエスケープと干渉しうる．
- `D_train` のような添字の語は `D_{\text{train}}` と書く．イタリック化を避けられる．
- 単位は `$3\ \mathrm{m\ s^{-1}}$`，期待値は `\mathbb{E}`．
- 著者所属の `^1,2` のような**数式でない上付き**は LaTeX ではなく `<sup>1,2</sup>` を使う．
- 書き終えたら KaTeX でパースを確認する (`npm i katex` して `katex.renderToString`)．
  ブラウザで開いて初めて壊れているのが分かる，という手戻りを防げる．

#### 例外

`.tex` 文書は当然 LaTeX (上の「LaTeX」節を参照) ．
ユーザーが明示的に表記を指定した場合は，常にその指示を優先する．

### 用語の表記 (読み手が対応表なしで読めるか)

**判断基準はひとつ．その語を初めて見た読み手が，対応表を持たずに意味を取れるか．**
取れないならそれは用語ではなく，自分だけに通じる略号である．

- **英単語を漢字一文字に置き換えて用語を作らない．** `window` を「窓」，`floor` を「床」，
  `seed` を「種」と書くたぐい．日本語として通用しないうえ，既存の語 (floor 関数，種類) と衝突する．
  2026-09-09 にメンターから実際に指摘を受けた．
- 優先順位は **定訳 > 英語・カタカナのまま > 概念を説明する語句**．定訳があれば定訳を使う．
  無ければ英語のまま使い，**無理に訳語を作らない**．どちらも無ければ 1 語に縮めず，
  「超えるべき基準値」のように説明する語句にする．
- **同じ語を 1 つの文書で 2 つの意味に使わない．** 訳語ではなく読み違いの問題になる．
- 専門用語は初出だけ「データ同化 (data assimilation)」の形で原語を併記し，以降は日本語だけにする．

| 悪い例 | なぜ駄目か | 良い例 |
|---|---|---|
| ウィンドウを「窓」と書く | 定訳があるのに直訳している | ウィンドウは `[2, 6, 12]` |
| 超えるべき床値 | 「床値」は日本語に無い造語 | 超えるべき基準値 |
| 300 epoch 収束済みの種 | 乱数シードと紛れる | 300 epoch 収束済みの元モデル |

#### 例外

**コードの識別子に対応する語は言い換えない．** 変数名・CLI フラグ・列名として実在する語
(`arm` に対する「アーム」など) を日本語側で言い換えると，コードと文書の対応が切れる．
そのまま使い，**初出で 1 回だけ「コードの `arm` に対応する実験系統」と対応を添える**．

### 🐍 Python 開発ガイドライン

Python コードを扱う際は、以下のルールを厳格に適用すること。

#### ツールチェーンと依存管理
- パッケージ管理には **`uv`** を使用すること。
- Linter/Formatter として `ruff`、型チェッカーとして `ty` を必須とする。
- これらは以下のコマンドで開発用依存として追加すること:

```bash
uv add --dev ruff ty
```

#### 品質基準 (Lint & Type Check)
- 提案するコードは、必ず ruff check、ruff format、および ty をパスさせること。
- 型ヒント (Type Hints): すべての関数引数と戻り値に型ヒントを記述すること。
- Docstring: すべてのモジュール、クラス、関数に簡潔な日本語の Docstring を記述すること。

#### ライブラリ固有のルール (Matplotlib)
- グラフ描画 (matplotlib) を行う際は、日本語フォント対応のために japanize_matplotlib を使用する。
- ruff による未使用 import 削除 (F401) を防ぐため、必ず以下の形式で記述する:

```Python
import japanize_matplotlib  # noqa: F401
import matplotlib.pyplot as plt
```

## 📋 行動ログ運用ルール (Logging Policy)

あなたは自律的にタスクを遂行する際、常にその進捗を `PROGRESS.md` というファイルに記録し続ける必要があります。
ユーザーが何が行われたかを後で追えるように、以下のタイミングで追記してください。

1. **タスク開始時**: 何を始めようとしているか。
2. **主要なコマンド実行後**: 成功したか、エラーが出たか、どう対処したか。
3. **ファイル変更時**: どのファイルをなぜ変更したか。
4. **完了時**: 最終的な成果。

### PROGRESS.md のフォーマット例

日時を含めて、以下のように追記してください。

```
- [YYYY-MM-DD HH:MM] 🚀 タスク「〇〇機能の実装」を開始しました。
- [YYYY-MM-DD HH:MM] 🔧 `utils.py` の `fix_data` 関数を修正しました（型エラーの解消のため）。
- [YYYY-MM-DD HH:MM] ✅ `uvx ruff check` がパスしました。
- [YYYY-MM-DD HH:MM] ⚠️ テストでエラーが発生したため、再修正を行います。
```

### 行数制限ルール (MANDATORY)

- **最大行数**: PROGRESS.md は **100行** を上限とする。
- **追記時の処理**: 新しいエントリを追加した結果、100行を超える場合は **古い行 (ファイル先頭) から削除** して100行以内に収める。
- **削除の単位**: 1エントリ (1行) 単位で削除する。複数行にまたがるエントリがある場合は、そのエントリ全体を削除対象とする。
- **空行の扱い**: 空行もカウントに含める。ただし、削除によって先頭に空行が残った場合は、それも削除する。

## 🚨 通知運用ルール(Notification Policy - MANDATORY)

タスク完了時は、以下のルールにしたがって必ずSlackへ報告を行うこと。
- 完了報告の強制: 長いタスク、コマンド実行、一連の思考や作業が完了した際は、ユーザーの指示を待たずに必ず **notify-slack** コマンド (`notify-slack "$1" "$2"`) を実行して Slack へ報告すること．
- 引数の仕様:
  - **$1**(Message):必須。「何をしたか」「結果(成功/失敗)」
  - **$2**(File):任意。生成されたプロット画像(.png)、レポート(.pdf)、重要なログファイルがある場合はパスを指定する。
- 使用例:
  - テキストのみ: **notify "モデルの学習が完了しました。精度は98%です"**
  - 画像付き: **notify "損失関数の推移プロットです" "./logs/loss_curve.png"**
- エラー時の対応:
  -処理の途中で失敗した場合も、エラー内部の要約を**notify**で送信すること
